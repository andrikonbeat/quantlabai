## Exploration: skill-format-negative-test

### Current State
The QuantLab skill format contract (REQ-904) requires every `SKILL.md` to include YAML frontmatter with `name`, `description`, `disable-model-invocation`, `user-invocable`, `license`, `metadata`, and a `## Execution Role` section. The parent change `opencode-harness-elevation` fixed the three QuantLab skills to comply, but left the negative test scenario ("Invalid format rejected") uncovered. The existing `tests/campaign/test_skill_sync.py` covers sync idempotency, drift detection, and allowlist scoping, but has zero format-validation coverage.

### Affected Areas
- `tests/campaign/test_skill_sync.py` — natural home for the new negative test; already loads `sync_skills.py` via `importlib` and uses `tmp_path` for isolated filesystem fixtures.
- `ai/opencode/sync_skills.py` — currently performs only byte-level sync and writes a minimal registry markdown; it does **not** parse or validate YAML frontmatter.
- `.atl/skill-registry.md` — generated by the external `gentle-ai skill-registry refresh` binary; this is the only component that actually parses SKILL.md frontmatter, and it renders missing/invalid frontmatter as `—` in the description column.
- `openspec/specs/skill-format/spec.md` — source of truth for REQ-904 required fields and acceptance criteria.

### Approaches
1. **Pure test-side frontmatter assertion** — write a pytest that directly parses a temp `SKILL.md` with a missing/invalid field and asserts the frontmatter is rejected.
   - Pros: no production code changes; self-contained; fast; deterministic; matches the "test-only follow-up" scope.
   - Cons: does not exercise the actual production validation path (the external `gentle-ai` binary); could drift if `gentle-ai` changes its rules.
   - Effort: Low

2. **External CLI invocation** — call `gentle-ai skill-registry refresh` (or a related subcommand) from pytest against a temp invalid skill, then assert the registry output flags it.
   - Pros: exercises the real validation pipeline end-to-end.
   - Cons: brittle (depends on external stripped Go binary); slow; requires `~/.config/opencode` isolation; hard to assert exact failure mode from binary output.
   - Effort: Medium

3. **Add validation helper to `sync_skills.py`** — extract a `validate_skill_frontmatter()` function (or similar) into the sync script, then unit-test it.
   - Pros: gives the repo a reusable validation primitive; testable in-process.
   - Cons: adds production code for a test-only change; scope creep beyond the stated objective.
   - Effort: Medium

### Recommendation
**Approach 1 (pure test-side assertion)** is the right fit. The change is explicitly scoped as a small, test-only follow-up. Adding a focused pytest in `tests/campaign/test_skill_sync.py` that creates a temp `SKILL.md` missing required frontmatter fields, parses the YAML block, and asserts the missing fields are detected is the minimal, reviewable path. It closes the REQ-904 warning without touching production code or depending on the external `gentle-ai` binary.

### Risks
- The test validates the **spec contract** (required fields), not the **production validator** (the external `gentle-ai` binary). If the binary’s validation rules diverge from the spec, the test will not catch that drift.
- If `gentle-ai` later moves validation into this repo, the test may need to be retargeted to call the new function directly.
- The test must avoid reading the real `~/.config/opencode/skills` tree; use `tmp_path` fixtures for isolation.

### Ready for Proposal
Yes. The orchestrator should tell the user: "We will add a single negative pytest to `tests/campaign/test_skill_sync.py` that creates a temp `SKILL.md` missing required frontmatter fields and asserts rejection. No production code changes. This closes the REQ-904 gap left open by the parent change."
