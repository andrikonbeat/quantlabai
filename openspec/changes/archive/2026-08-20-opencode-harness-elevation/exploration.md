# Exploration: opencode-harness-elevation

Elevate the QuantLab OpenCode harness to the prompt-engineering discipline level of the gentle-ai harness, across 8 items: router-prompt versioning, skills sync, project AGENTS.md, post-phase gatekeeping, lossless gate discipline, 4R review for SDK changes, thin-skill upgrades, and model assignments.

## Current State

The harness has two layers: repo-canonical files under `ai/opencode/` (prompts in `agents/`, one skill under `skills/`) and live files under `~/.config/opencode/` (19 quantlab prompts, 3 quantlab skills, global config). `sync_prompts.py` (REQ-806/807/810/821) keeps the 16 managed prompts byte-parity with the live dir, deterministic and idempotent, with `--dry-run`/`--check`. The campaign loop (`campaign.md` + `quantlab-run-campaign` SKILL.md, which duplicate each other) delegates each of the 14 phases (REQ-37) to `quantlab-phase-*` subagents, validates the `PhaseResult` envelope shape (`validate_phase_result`, REQ-802), and halts only on `status != success` — no artifact-existence or input-drift checks. Human gates resolve through the AD-4 decision-file protocol (`pending.json` → `decision.json`), fail-closed (REQ-11), but without allowed-answer-domain validation or lossless re-presentation. gentle-ai 2.4.0 is installed with the full native review lifecycle (`review start/status/capture-result/inspect-candidate/finalize/validate/mode/repair`); this repo currently has 3 active `reviewing` lineages, 5 invalid ones, quarantined terminal lineages, and RDD mode OFF (clone-local). No `agent.model` is set anywhere; the active model is `opencode/deepseek-v4-flash-free`; providers configured in auth.json are opencode, nvidia, cloudflare-workers-ai, kilo, groq, openrouter.

### 4. Post-phase gatekeeper

- Model = gentle-ai issue #870 (Automatic Mode Gatekeeper): validates **contract conformance, artifact existence (reads the artifact back), hallucinated references, input drift, routing coherence**; hybrid cost-aware (inline for low-risk, fresh-context delegated review for high-risk); **on gate failure re-runs the phase exactly once with corrective feedback, then stops and reports**.
- Current loop (campaign.md lines 113-129): `validate_phase_result(result)` (shape only, delegation.py REQ-802) → fold → `if result.status != "success": halt_and_escalate`. No artifact read-back, no drift check, no hallucinated-ref check, no exactly-once re-run.
- `campaign.md` and `quantlab-run-campaign/SKILL.md` duplicate the loop content — **dual-source drift has already materialized** (the live skill lost the preflight section). Any gatekeeping text added to only one of them will drift again.

### 5. Lossless discipline in gates

- Current protocol (campaign.md Gate Protocol AD-4, each phase prompt's "Human Gates (fail-closed)" section, guardian-orchestrator.md `HUMAN_APPROVE_REPLACEMENT`): write `{gate_id}.pending.json`, present via `question`, read `{gate_id}.decision.json`, `action == "approve"` ONLY, fail-closed (REQ-11), campaign-id regex `[A-Za-z0-9_-]`. SDK side: `DecisionsFileGateCallback`/`read_decision_file` (fail-closed, never auto-approve).
- Missing: complete choice-envelope preservation, exact allowed-answer domain validation (accept EXACTLY ONE option; reject zero/multiple), and re-present + STOP on invalid input.
- The lossless blocking-prompt model to adapt is the gentle-ai consent envelope: `review-ledger-contract.md` describes the typed `gentle-ai.review-integration.consent/v3` envelope handled as a Lossless Blocking Prompt — preserve groups/order, selection mode, exact allowed-answer domain, machine answer tokens (`granted`/`declined`) never translated, present the complete semantic envelope once, then run exactly the one follow-up for the human's answer and STOP.
- Codified in `openspec/specs/human-gates/spec.md` (REQ-38/REQ-11) and `openspec/specs/guardian-orchestrator/spec.md` (REQ-824).

- The change should document/configure the lifecycle for `sdk/quantlab/` work (consent envelope + stop-reason table as the reference), NOT enable RDD mode (user-owned decision). No repo docs currently describe `gentle-ai review` for QuantLab; CI runs only `./sdk` tests, so review gates are not CI-wired today.

## Approaches

### Items 1-2: sync extension (prompts + skills)

1. **Extend `sync_prompts.py` with a skills section** — add `orchestrator.md`/`deploy.md`/`monitor.md` to `MANAGED_NAMES` and add a parallel skills allowlist (dir-by-dir copy) with `--dry-run`/`--check` covering both.
   - Pros: one tool, one test file, one CI hook; reuses proven determinism/idempotency machinery.
   - Cons: mixes concerns (flat prompt files vs skill directories with different live roots); docstring/REQ framing is prompts-specific; script grows.
   - Effort: Medium

2. **Sibling `sync_skills.py` mirroring the same discipline** — prompts and skills each get a dedicated deterministic idempotent sync with allowlist, dry-run, check; optionally share a small helper module.
   - Pros: separation of concerns; skills semantics (dirs, frontmatter, registry interaction) get their own contract and tests; prompts script untouched except allowlist add.
   - Cons: duplicated boilerplate unless a shared helper is extracted; two scripts to maintain.
   - Effort: Medium

   **Recommendation: Option 2** (sibling `sync_skills.py`, extracting a tiny shared helper if boilerplate repeats). Drift policy: **repo wins** on first sync (the repo copy of `quantlab-run-campaign` is the newer, correct one — restore the preflight). Item 7 then creates repo copies of the two thin skills so the sync allowlist covers exactly the repo-managed skills.

### Items 4-5: campaign.md vs SKILL.md as canonical home

1. **Keep both, edit both consistently** — add gatekeeper + lossless gate text to campaign.md AND the skill.
   - Pros: no structural change.
   - Cons: dual-source drift already proven (live skill lost REQ-37 preflight); guaranteed divergence over time.
   - Effort: Low now, recurring forever.

2. **Dedup: campaign.md canonical, SKILL.md becomes a condensed executor contract** — campaign.md holds the full loop/gate/exit contract (it is already the richer source); the skill keeps frontmatter, orchestrator gate, executor override, lifecycle overview, files list, and a pointer to `ai/opencode/agents/campaign.md` (mirroring how the SDD skills defer to `_shared`).
   - Pros: single source of truth; sync discipline (item 2) then enforces parity of one canonical file; matches the gentle-ai pattern the objective asks for.
   - Cons: changes the skill's role; requires updating the skill-resolver hardcoded path to keep pointing at the live skill (it stays valid).
   - Effort: Medium

   **Recommendation: Option 2** — campaign.md is the canonical contract; the skill defers. The gatekeeper (item 4) and lossless gate protocol (item 5) are then written once, in campaign.md, and the skill references them. Guard: the skill's "Executor Override" + files section still tells the executor where the canonical contract lives.

### Item 6: review integration surface

1. **Docs-only** — add a `docs/guides/review-lifecycle.md` (or section in an existing guide) describing `gentle-ai review start --consent ... --locale en` flow for SDK changes, the consent-envelope handling (lossless blocking prompt, machine tokens `granted`/`declined`), and the stop-reason-code table (copied from `review-ledger-contract.md`); do NOT enable RDD.
   - Pros: zero behavioral risk; documents reality (lifecycle exists, mode off).
   - Cons: no enforcement.
   - Effort: Low

2. **Docs + CI/authority hygiene** — docs as above, plus a note/handling for the existing invalid/quarantined lineages (`gentle-ai review repair --preflight` guidance) and an optional CI job running `sync_prompts.py --check` for prompt/skill parity.
   - Pros: closes the parity CI gap; surfaces authority debt.
   - Cons: authority repair is a user decision (mode enable/repair are user-owned); CI job needs the live config present (may not exist on CI runners — parity check against a committed manifest instead).
   - Effort: Medium

   **Recommendation: Option 2 scoped** — docs (consent envelope + stop-reason table, lifecycle route for SDK changes) + a CI-safe parity check. RDD enable/repair stays user-owned and explicitly out of this change.

### Item 8: model assignments location

1. **Repo `opencode.json` agent overrides** — add `model` to each quantlab agent block in the repo config (OpenCode merges project over global).
   - Pros: reviewable in-repo, CI-verifiable, survives reinstall.
   - Cons: merge semantics for partial agent blocks need validation; repo config currently stub-only.
   - Effort: Low (after merge validation)

2. **Documented global-config edits** — the apply phase edits `~/.config/opencode/opencode.json` directly per a spec'd table.
   - Pros: single config source; no merge-semantics risk.
   - Cons: out-of-repo mutation, not versioned, not CI-verifiable; drift risk on reinstall.
   - Effort: Low

   **Recommendation: Option 1** (validate merge during design), with the concrete cheap/expensive model names confirmed by the user (budget decision). Cheap default for the 14 phase agents + guardian/alert/replacement; expensive for `quantlab-orchestrator`, `quantlab-campaign`, `guardian-orchestrator`.

## Risks

- **Orphaned router prompts**: `deploy.md`/`monitor.md` are unbound to any agent — versioning them preserves dead files; the change should decide explicitly (version-as-legacy vs. delete) and record it in the proposal, or the sync allowlist will carry files nothing binds.
- **Test flips**: `test_prompt_sync.py` encodes REQ-821's exclusion; the delta spec MODIFIED must be applied in the same change as the test flips or the suite goes red.
- **Dual-source drift**: campaign.md and the skill already diverged once; without dedup (approach 2, items 4-5) gatekeeping/lossless text will drift again.
- **Skills sync direction**: repo-wins is the only safe policy given the drift; a reverse edit in live would be silently reverted — document that live hand-editing of synced skills is not permitted (same contract as prompts).
- **Review authority debt**: 5 invalid + quarantined lineages exist; docs must reference `gentle-ai review repair --preflight` and the mode kill switch without enabling anything.
- **Model selection**: concrete cheap/expensive model names are a user budget decision; defaulting without confirmation may incur cost or break (provider/model strings must be real).
- **CI parity check**: the live `~/.config/opencode/` dir may not exist on CI runners — a parity check there would false-fail; use a committed manifest or gate the job on the dir existing.
- **Global config drift**: if item 8 lands as global-config edits, reinstallation or config restore (`opencode.json.bak-*` present) can silently lose the assignments.
